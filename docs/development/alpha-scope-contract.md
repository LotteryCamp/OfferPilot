## 1. 目的与产品边界

本文冻结 Alpha 核心流程的范围、对象语义、状态流转和验收条件，供前端、后端、Agent、来源处理与测试共同使用。内容依据仓库 `docs/design/product/OfferPilot_产品方案.md`、需求流程说明、Agent 集成设计及数据库设计整理；若实现细节尚未确定，应由相关负责人在实现 PR 中补充，不得改变以下业务边界。

OfferPilot 是面向大学生个人事务的工作站。产品规划覆盖推免、竞赛、科研或创新项目、奖学金和评优等场景；本次 Alpha 只打通一个推免示例的个人流程。竞赛仅提供领域规则与验收样例，不承诺完成独立竞赛业务闭环。

本阶段演示主流程：

> 创建个人事项 → 获取一份公开来源 → Agent 提取要求并保留出处、适用范围和缺口 → 生成待审阅的候选计划 → 用户确认或拒绝 → 确认后创建并查看个人任务。

产品原则：

- 所有事项、任务、个人资料和用户决定属于当前用户；不包含团队工作区、成员邀请、他人任务分派或多人审核。
- 官方网页或文件可作为公开来源。Agent 的提取和程序校验只表示机器处理状态，不表示官方核实、资格认定或结果保证。
- 用户上传的截图、转载、经验和笔记属于当前用户的事项线索；它们不转入共享官方信息层。
- 候选计划在用户确认前不是正式任务。用户拒绝或暂缓时不得创建正式任务。
- 官方报名、联系导师、材料提交等对外办理由用户自行完成；Alpha 不代替用户向外部渠道提交。
- 原型、静态数据、设计稿和未运行的代码不能作为已实现或已验收的证据。

## 2. Alpha 范围

| 本阶段纳入 | 本阶段不承诺 |
| :--- | :--- |
| 创建和读取一个推免个人事项 | 完整登录、账户体系和多租户产品化部署 |
| 读取约定的一份公开 HTML 通知或规则样例 | 任意网页、扫描 PDF 和复杂附件的通用解析 |
| 保存来源链接、获取时间、适用范围和原文定位信息 | 全国院校政策完整覆盖、定期巡检和自动政策更新 |
| Agent 输出结构化候选要求/计划、出处和未解决缺口 | 把自动提取结果表述成官方核实或正式资格结论 |
| 用户确认后将候选计划转为个人任务 | 自动报名、联系导师、发送邮件或提交材料 |
| 用户拒绝候选计划后不创建任务 | 材料改写、真实 DOCX 导出和完整竞赛流程 |
| 显示处理中、成功、待核对和失败等基本状态 | 完整后台管理和生产级运维能力 |

若 Alpha 当前没有登录能力，运行范围必须明确标记为“单用户本地演示”。此限制不能被描述为已具备跨账户隔离；数据访问边界仍须通过事项关联与服务端校验落实，无法实现的验收项应标为未完成。

## 3. 术语与对象契约

以下字段是跨模块的业务字段与语义基线，不强制具体编程语言、数据库类型或 HTTP 路径。字段名可在技术实现中转换命名格式，但含义、状态和关联关系须保持一致。

| 对象 | 必需字段 | 语义与约束 |
| :--- | :--- | :--- |
| 个人事项 `Matter` | `id`、`workspace_id`、`type_code`、`template_version_id`、`goal`、`status`、`scope_year`、`scope_attrs` | 对应 `core.matter`。`type_code` 本轮为推免；事项属于个人工作区。目标院校或批次不同且适用范围不同的，应分开建事项。 |
| 来源及快照 `SourceReference` | 来源：`id`、`publisher`、`url`、`scope`、`scope_year`、`status`、`auto_check_status`；快照：`id`、`source_id`、`version_no`、`content_hash`、`extraction`、`fetched_at` | 对应 `ops.source` 与 `ops.snapshot`。官方来源及快照与事项要求通过快照关联；用户上传的截图、转载或笔记保存在 `core.matter_info_item`，仍属于当前用户和事项。 |
| 候选要求 `Requirement` | `id`、`matter_id`、`snapshot_id`、`field_key`、`label`、`obligation_nature`、`extract_status`、`scope`、`value_text`、`confidence` | 对应 `core.requirement`。关键要求关联来源快照，出处定位由 `ops.evidence` 表达；缺少范围或依据时记录 `ops.source_gap`。机器状态不等于官方核实。 |
| 候选计划 `CandidatePlan` | `id`、`matter_id`、`version_no`、`status`、`basis_version`、`generated_at`、`op_id` | 对应 `core.candidate_plan`。计划内容须可审阅并关联事项、依据版本与操作标识；正式任务与候选计划分开保存。 |
| 个人任务 `Task` | `id`、`matter_id`、`plan_id`、`executor_id`、`title`、`due_at`、`status`、`depends_on` | 对应 `core.task`。仅用户确认候选计划后创建；可追溯到事项和被确认的计划。 |
| 用户决定 `PlanDecision` | `id`、`plan_candidate_id`、`decision`、`decided_at` | 记录确认或拒绝。重复提交同一决定须幂等，不得重复生成任务。 |

### 3.1 状态定义

| 对象/字段 | 允许值 | 说明 |
| :--- | :--- | :--- |
| 事项状态 `matter_status` | `draft`、`active`、`paused`、`archived`、`cancelled` | 与数据库设计的 `matter_status` 一致。 |
| 来源自动检查状态 `check_result` | `pending`、`passed`、`failed`、`conflict` | 对应 `ops.source.auto_check_status`。`passed` 只表示程序定义的检查项通过，不表示官方核实或内容必然正确。 |
| 要求提取状态 `extract_status` | `extracted`、`checked`、`to_review`、`rejected` | 与数据库设计一致。`checked` 表示已执行约定的检查，不代表官方认证；未解决关键疑点须保持待核对。 |
| 候选计划状态 `plan_status` | `draft`、`pending`、`confirmed`、`rejected`、`expired` | 与数据库设计一致。只有 `confirmed` 可以生成正式任务；`draft`、`pending`、`rejected`、`expired` 不得生成任务。 |
| 正式任务状态 `task_status` | `pending`、`ready`、`in_progress`、`blocked`、`done`、`cancelled` | 与数据库设计一致。`done` 只表示个人工作站中的任务完成，不代表外部机构办理结果。 |
| 计划项义务性质 `obligation_nature` | `required`、`advised`、`optional`、`to_verify` | 与数据库设计一致；需结合来源解释。无法确定时使用 `to_verify`，不推断为必需或可选。 |

### 3.2 时间与依据

- `due_at` 只在来源给出可确定的日期/时间时填写；来源只写日期时不得擅自补写确定时刻。
- `deadline_basis` 记录该时间的来源标识及原文定位；个人建议准备日期须与官方截止日期分开表达。
- 适用范围至少能表达通知年度、对象/项目，以及必要的学院、专业、批次或路径。Alpha 样例不适用的维度可以为空，但不能隐藏未知范围。
- Agent 无法确认内容时应返回具体 `gap`，而不是生成貌似完整的确定结论。

## 4. 模块交互契约

| 步骤 | 输入 | 输出/状态变化 | 责任模块 |
| :--- | :--- | :--- | :--- |
| 创建事项 | 目标、类型及用户已知的适用信息 | 持久化 `core.matter`，返回事项标识 | 前端、后端业务 |
| 获取来源 | 事项标识、约定公开 URL | 建立或关联 `ops.source` 与 `ops.snapshot`，包含检查状态、获取时间和内容定位；失败返回明确缺口 | 来源处理、后端数据 |
| 生成候选 | 事项、来源快照、规则样例 | 生成 `core.requirement`、`core.candidate_plan`；保留出处、范围、缺口和机器状态 | Agent 编排、模型适配 |
| 查看候选 | 事项标识 | 返回候选内容和 `pending` 状态 | 后端、前端 |
| 拒绝候选 | 候选标识、用户决定 | 记录 `rejected`，不创建 `core.task` | 前端、后端业务 |
| 确认候选 | 候选标识、用户决定 | 记录 `confirmed`，按确认计划创建个人任务并返回结果 | 前端、后端业务、数据层 |
| 重试确认 | 已处理过的同一候选确认请求 | 返回既有结果，不重复创建任务 | 后端业务、数据层 |
| 读取任务 | 事项标识 | 返回该事项下的个人任务及当前状态 | 后端业务、前端 |

实现可采用现有项目接口风格。接口命名、请求/响应示例和错误码由前后端负责人在同一 PR 或相邻 PR 中补充，必须与本节业务语义一致。

## 5. 验收基线

每个场景由执行人记录实际命令/操作、输入数据、观察结果和通过状态。未运行、只检查静态代码或依赖模拟数据的场景不得标记为通过。

| 编号 | 场景 | 通过条件 |
| :--- | :--- | :--- |
| A-01 | 新建推免事项 | 新事项获得稳定标识，可通过读取操作再次取得；工作区显示该事项。 |
| A-02 | 读取约定公开来源 | 返回 URL、标题、获取时间、适用范围和原文定位；页面可回看出处。 |
| A-03 | 来源读取失败 | 返回明确失败/缺口状态；不生成读取成功或规则正确的假结论。 |
| A-04 | Agent 生成候选要求/计划 | 响应满足对象契约；要求和计划项能关联来源；未知信息以缺口呈现。 |
| A-05 | 候选计划待用户确认 | 运行状态显示“等待确认”，计划状态为 `pending`，正式任务列表中不存在该候选对应任务。 |
| A-06 | 用户拒绝候选计划 | 决定记录为 `rejected`；正式任务数量不因拒绝而增加。 |
| A-07 | 用户确认候选计划 | 决定记录为 `confirmed`；对应任务可创建并重新读取。 |
| A-08 | 重复确认同一候选 | 重试返回一致结果，任务不重复创建。 |
| A-09 | 模型超时或响应无效 | 调用状态清楚标为失败/待处理，不保存伪造的候选成功结果。 |
| A-10 | 事项数据边界 | 只能读取与当前演示身份/事项边界相符的数据；若无登录，文档明确单用户本地演示限制并验证事项关联。 |
| A-11 | 前端主流程 | 用户可从创建事项进入工作区，查看来源与候选，作出决定并看到确认后的任务；加载、空状态和错误状态均有反馈。 |
| A-12 | 启动与复现 | 新环境按 README 执行步骤可启动所交付模块；PR 记录实际运行命令和结果。 |

### 5.1 Alpha 完成定义

- 从创建事项到任务展示的主路径能够本地运行；使用真实模块调用，不以静态原型或固定成功数据替代。
- 候选与正式任务的数据边界明确；确认、拒绝、重复请求和失败状态符合上述契约。
- 来源、适用范围、缺口和机器处理状态可以查看，机器状态不冒充官方核实。
- 核心正常路径与至少一个关键异常路径有可复现验证记录。
- 未实现功能、未通过测试和单用户演示限制在 README、PR 或验收记录中如实说明。

## 6. 不纳入本次验收的能力

下列规划能力仍属于产品后续方向，不作为本次 Alpha 的完成条件：完整推免全流程、完整竞赛闭环、其他大学生事项模板、人工复核团队或共享资料库、材料智能改写与 DOCX 导出、自动报名/联系/外部提交、全国政策覆盖、定期巡检、生产级多用户部署。
