## 1. 目的与产品边界

本文冻结核心流程的范围、对象语义、状态流转和验收条件，供前端、后端、Agent、来源处理与测试共同使用。内容依据仓库 `docs/design/product/OfferPilot_产品方案.md`、需求流程说明、Agent 集成设计及数据库设计整理；若实现细节尚未确定，应由相关负责人在实现 PR 中补充，不得改变以下业务边界。

OfferPilot 是面向大学生个人事务的工作站。产品规划覆盖推免、竞赛、科研或创新项目、奖学金和评优等场景；当前基线只覆盖一个推免示例的个人流程。竞赛仅提供领域规则与验收样例，不承诺完成独立竞赛业务闭环。

核心流程：

> 创建个人事项 → 获取一份公开来源 → Agent 提取要求并保留出处、适用范围和缺口 → 生成待审阅的候选计划 → 用户确认或拒绝 → 确认后创建并查看个人任务。

产品原则：

- 所有事项、任务、个人资料和用户决定属于当前用户；不包含团队工作区、成员邀请、他人任务分派或多人审核。
- 官方网页或文件可作为公开来源。Agent 的提取和程序校验只表示机器处理状态，不表示官方核实、资格认定或结果保证。
- 用户上传的截图、转载、经验和笔记属于当前用户的事项线索；它们不转入共享官方信息层。
- 候选计划在用户确认前不是正式任务。用户拒绝或暂缓时不得创建正式任务。
- 官方报名、联系导师、材料提交等对外办理由用户自行完成；系统不代替用户向外部渠道提交。
- 原型、静态数据、设计稿和未运行的代码不能作为已实现或已验收的证据。

## 2. 范围

| 纳入范围 | 不承诺范围 |
| :--- | :--- |
| 注册、登录、个人工作区、管理员账户管理，以及一个推免个人事项的创建与读取 | 邮件验证、找回密码与 MFA |
| 读取约定的一份公开 HTML 通知或规则样例 | 任意网页、扫描 PDF 和复杂附件的通用解析 |
| 保存来源链接、获取时间、适用范围和原文定位信息 | 全国院校政策完整覆盖、定期巡检和自动政策更新 |
| Agent 输出结构化候选要求/计划、出处和未解决缺口 | 把自动提取结果表述成官方核实或正式资格结论 |
| 用户确认后将候选计划转为个人任务 | 自动报名、联系导师、发送邮件或提交材料 |
| 用户拒绝候选计划后不创建任务 | 材料改写、真实 DOCX 导出和完整竞赛流程 |
| 显示处理中、成功、待核对和失败等基本状态 | 完整后台管理 |

账户管理已纳入后端范围。每个账户拥有独立个人工作区，数据访问边界通过登录会话、事项关联、服务端校验与行级安全落实。管理员仅扩展账户管理权限，不读取其他用户的私人业务数据。

## 3. 术语与对象契约

以下字段是跨模块的业务字段与语义基线，不强制具体编程语言、数据库类型或 HTTP 路径。字段名可在技术实现中转换命名格式，但含义、状态和关联关系须保持一致。

| 对象 | 必需字段 | 语义与约束 |
| :--- | :--- | :--- |
| 个人事项 `Matter` | `id`、`workspace_id`、`type_code`、`template_version_id`、`goal`、`status`、`scope_year`、`scope_attrs` | 对应 `core.matter`。`type_code` 当前为推免；事项属于个人工作区。目标院校或批次不同且适用范围不同的，应分开建事项。 |
| 来源及快照 `SourceReference` | 来源：`id`、`publisher`、`url`、`scope`、`scope_year`、`status`、`auto_check_status`；快照：`id`、`source_id`、`version_no`、`content_hash`、`extraction`、`fetched_at` | 对应 `ops.source` 与 `ops.snapshot`。官方来源及快照与事项要求通过快照关联；用户上传的截图、转载或笔记保存在 `core.matter_info_item`，仍属于当前用户和事项。 |
| 候选要求 `Requirement` | `id`、`matter_id`、`snapshot_id`、`field_key`、`label`、`obligation_nature`、`extract_status`、`scope`、`value_text`、`value_type`、`confidence` | 对应 `core.requirement`。`value_type` 使用 `text`、`date`、`number`、`boolean`、`enum`；关键要求关联来源快照，出处定位由 `ops.evidence` 表达，缺口由 `ops.source_gap` 记录。机器状态不等于官方核实。 |
| 候选计划 `CandidatePlan` | `id`、`matter_id`、`version_no`、`status`、`basis_version`、`generated_at`、`op_id`（确认前为空） | 对应 `core.candidate_plan`。`basis_version` 标识生成时依据；候选计划及其计划项须持久化，不能依赖请求进程内存。迁移需增加 `expired_at`，并修正状态时间约束：仅 `confirmed` 要求 `confirmed_at`，仅 `expired` 要求 `expired_at`。 |
| 候选计划项 `CandidatePlanItem` | `id`、`plan_id`、`seq`、`title`、`obligation_nature`、`official_deadline_date`、`official_deadline_at`、`suggested_date`、`depends_on_item_ids`、`evidence_required` | 所需 schema 扩展。每项在确认前即可保存和读取；`CandidatePlanItemSource` 关联 `source_id`、`snapshot_id`、原文定位和短引文，供审阅时回看依据。 |
| 个人任务 `Task` | `id`、`matter_id`、`plan_id`、`plan_item_id`、`executor_id`、`title`、`due_at`、`official_deadline_date`、`official_deadline_at`、`suggested_date`、`status`、`depends_on` | 对应 `core.task` 并扩展计划项关联及期限字段。仅用户确认后创建；通过 `plan_item_id` 可追溯到原候选项及其来源定位。 |
| 计划决定 `CandidatePlanDecision` | `id`、`plan_id`、`decision`、`decided_by`、`decided_at`、`operation_id` | 所需 schema 扩展。决定直接关联被确认或拒绝的候选版本；`decision` 为 `confirmed` 或 `rejected`。事项级的 `core.matter_decision` 继续记录 adopt/later/skip，不替代此记录。每个候选版本至多有一条终态决定；`operation_id` 保存该次请求的幂等键。 |

### 3.1 状态定义

| 对象/字段 | 允许值 | 说明 |
| :--- | :--- | :--- |
| 事项状态 `matter_status` | `draft`、`active`、`paused`、`archived`、`cancelled` | 与数据库设计的 `matter_status` 一致。 |
| 来源自动检查状态 `check_result` | `pending`、`passed`、`failed`、`conflict` | 对应 `ops.source.auto_check_status`。`passed` 只表示程序定义的检查项通过，不表示官方核实或内容必然正确。 |
| 来源生命周期状态 `source_status` | `active`、`withdrawn`、`invalid` | 对应 `ops.source.status`。描述来源记录是否可继续使用；与自动检查状态分开，`active` 不表示内容已核实。 |
| 要求提取状态 `extract_status` | `extracted`、`checked`、`to_review`、`rejected` | 与数据库设计一致。`checked` 表示已执行约定的检查，不代表官方认证；未解决关键疑点须保持待核对。 |
| 候选计划状态 `plan_status` | `draft`、`pending`、`confirmed`、`rejected`、`expired` | 与数据库设计一致。只有 `confirmed` 可以生成正式任务；`draft`、`pending`、`rejected`、`expired` 不得生成任务。 |
| 正式任务状态 `task_status` | `pending`、`ready`、`in_progress`、`blocked`、`done`、`cancelled` | 与数据库设计一致。`done` 只表示个人工作站中的任务完成，不代表外部机构办理结果。 |
| 计划项义务性质 `obligation_nature` | `required`、`advised`、`optional`、`to_verify` | 与数据库设计一致；需结合来源解释。无法确定时使用 `to_verify`，不推断为必需或可选。 |

`Requirement.value_text` 按 `value_type` 使用规范值：`text` 为保留原意的文本；`date` 为 ISO 8601 日期 `YYYY-MM-DD`；`number` 为不带千位分隔符的十进制数，单位保留在来源/字段元数据；`boolean` 仅为 `true` 或 `false`；`enum` 保留来源中的单一选项文本，不自行映射成未约定编码。

### 3.2 时间与依据

- `official_deadline_date` 保存来源明确给出的日期；`official_deadline_at` 只在原文给出时刻时填写。
- `due_at` 仅在具体任务的执行期限确实有确定时刻时填写；不得为 date-only 的官方期限虚构时刻。
- `suggested_date` 只表示 Agent 给出的个人建议准备日，与官方期限分列。
- 每项官方期限通过 `CandidatePlanItemSource` 保留来源标识、快照版本、原文定位及引文；确认后任务经 `plan_item_id` 延续该证据链。
- `basis_version` 是对规范化 JSON 输入计算的 SHA-256。输入固定包含事项适用范围及其版本、模板版本、领域规则包/规则版本、纳入候选的要求 ID 与版本、来源 ID/生命周期状态/所用快照版本及内容哈希、相关已确认个人事实 ID/版本，以及 Agent 输出契约和计划策略版本；对象键按字典序排列，数组按稳定 ID 排序，保留显式空值，以 UTF-8 紧凑 JSON 编码。生成时间、请求随机 ID 和模型自由文本不进入指纹。保存完整规范化输入，供确认时重算及审计。
- 确认时基于当前事项重新计算同一指纹；任一纳入依据发生新增、修改、撤回、失效或版本替换，或指纹不一致，候选即转 `expired`，仅写 `expired_at`，不写确认决定或任务。来源当前状态不可用、关键缺口未解决，或官方期限已过，也必须阻止确认。重新生成候选后由用户重新审阅。
- 适用范围至少能表达通知年度、对象/项目，以及必要的学院、专业、批次或路径。样例不适用的维度可以为空，但不能隐藏未知范围。
- Agent 无法确认内容时应返回具体 `gap`，而不是生成貌似完整的确定结论。

## 4. 模块交互契约

| 步骤 | 输入 | 输出/状态变化 | 责任模块 |
| :--- | :--- | :--- | :--- |
| 创建事项 | 目标、类型及用户已知的适用信息 | 持久化 `core.matter`，返回事项标识 | 前端、后端业务 |
| 获取来源 | 事项标识、约定公开 URL | 建立或关联 `ops.source` 与 `ops.snapshot`，包含生命周期、自动检查状态、获取时间和内容定位；失败返回明确缺口 | 来源处理、后端数据 |
| 生成候选 | 事项、来源快照、规则样例 | 生成 `core.requirement`、`core.candidate_plan` 和持久化计划项/来源关联；生成后可按事项及候选标识重新读取 | Agent 编排、模型适配、数据层 |
| 查看候选 | 事项标识、候选标识 | 返回候选内容、按序计划项、每项出处和 `pending` 状态 | 后端、前端 |
| 拒绝候选 | 候选标识、稳定的 `Idempotency-Key` | 在事务中记录候选级 `rejected` 决定并置候选状态为 `rejected`，不创建 `core.task` | 前端、后端业务、数据层 |
| 确认候选 | 候选标识、稳定的 `Idempotency-Key` | 重算并比对 `basis_version`；一致时在单一事务中记录确认决定、写入 `op_id` 并按计划项创建任务 | 前端、后端业务、数据层 |
| 重试确认/拒绝 | 同一候选及同一 `Idempotency-Key` | 返回已持久化的决定和任务结果，不重复创建；已终结候选遇到新 key 返回冲突及既有状态，不得重复写入或改变决定 | 后端业务、数据层 |
| 读取任务 | 事项标识 | 返回该事项下的个人任务、期限精度及沿 `plan_item_id` 可回看的来源定位 | 后端业务、前端 |

### 4.1 数据库实施约束

数据库结构须满足以下约束，候选内容才能跨请求/重启恢复：

- 建立候选计划项持久化表和候选项来源关联表。每项存储稳定 ID、顺序、标题、义务性质、官方日期/时刻、建议准备日、依赖、所需完成证据及 `source_id`、`snapshot_id`、原文定位、短引文。
- `core.candidate_plan_item` 的主键为稳定候选项 ID，`UNIQUE(plan_id, seq)`；来源关联以候选项、快照和原文定位组成唯一键。候选项依赖只允许引用同一计划内的候选项。
- `core.task` 增加 `plan_item_id` 唯一关联及官方期限日期、官方期限时刻、建议准备日字段；建议以 `UNIQUE(plan_item_id)` 阻止并发重试创建重复任务。任务读取可经计划项来源关系返回其原始依据。
- 增加候选计划决定记录，外键指向 `candidate_plan.id`，保存确认/拒绝、操作者、时间和 `operation_id`；`UNIQUE(plan_id)` 保证一个候选版本只有一个终态决定，`UNIQUE(operation_id)` 保证同一幂等键不被复用。`core.candidate_plan.op_id` 保持可空，确认成功时写入与决定相同的操作 ID；拒绝不写该字段。
- 候选生成时 `candidate_plan.op_id` 为空；仅确认成功时写入该字段。确认或拒绝请求使用 UUID 格式的 `Idempotency-Key`，首次请求生成，重试必须原样复用；同一 key 不得用于其他候选或操作。确认决定与全部任务在同一数据库事务提交。相同候选、相同 key 返回既有结果；不同 key 再次操作已终结候选时返回冲突和既有状态。
- 决定事务先校验归属和已有决定，再锁定候选并检查 `pending` 状态、当前依据及期限；依据更新与确认须遵循同一并发控制规则，防止检查后、写入前发生变化。相同 key 携带不同候选或决定时返回冲突。计划进入 `pending` 后内容及来源关联冻结；修改内容必须生成新候选版本。
- 为 `core.candidate_plan` 增加 `expired_at`，修正现有确认时间约束，避免把过期错误地当作已确认；过期只记录过期时间，不创建决定记录或任务。
- 候选计划项和来源关系在确认前就可持久化、读取和审阅，不能等到创建正式任务时才保存。

实现可采用现有项目接口风格。接口命名、请求/响应示例和错误码由前后端负责人在同一 PR 或相邻 PR 中补充，必须与本节业务语义一致。

## 5. 验收基线

每个场景由执行人记录实际命令/操作、输入数据、观察结果和通过状态。未运行、只检查静态代码或依赖模拟数据的场景不得标记为通过。

| 编号 | 场景 | 通过条件 |
| :--- | :--- | :--- |
| A-01 | 新建推免事项 | 新事项获得稳定标识，可通过读取操作再次取得；工作区显示该事项。 |
| A-02 | 读取固定官方来源样例 | 使用 `FX-S4-2027-FZU-MATH` 固定输入，返回来源 URL、标题、发布日、适用范围、快照版本及第（5）项定位；历史回放模式保留其已过期状态。 |
| A-03 | 来源读取失败 | 返回明确失败/缺口状态；不生成读取成功或规则正确的假结论。 |
| A-04 | Agent 生成候选要求/计划 | 对固定摘录提取 2027 届福州大学数学与统计学院校内推荐范围、2026-09-10 15:00（Asia/Shanghai）前提交，以及申请表、科研/竞赛证明和成绩单要求；每项关联固定快照和原文位置。仅在隔离测试库和固定时钟 2026-09-09 09:00（Asia/Shanghai）回放，不作为当前报名建议或生产数据。 |
| A-05 | 候选计划待用户确认 | 运行状态显示“等待确认”，计划状态为 `pending`；重读候选仍返回同一组计划项和出处，正式任务列表无对应任务。 |
| A-06 | 用户拒绝候选计划 | 候选级决定记录包含计划标识、`rejected`、操作者和时间；正式任务数量不因拒绝增加。 |
| A-07 | 用户确认候选计划 | 确认前重新计算依据指纹。指纹未变时在同一事务记录决定并写入任务；任务可重新读取并沿 `plan_item_id` 回看来源。 |
| A-08 | 并发或丢失响应后的确认重试 | 同一幂等键返回相同决定和任务 ID；计划项对应的任务唯一，不重复创建；终态候选不能用新 key 改写决定。 |
| A-09 | 候选生成后来源/规则/已确认事实版本改变 | 依据指纹的任一输入版本变化时拒绝确认，候选转为 `expired` 并写 `expired_at`，不写决定或任务，提示重新生成。 |
| A-10 | 官方日期/时刻、建议日期与来源追溯 | 精确时刻存入 `official_deadline_at`；date-only 仅存 `official_deadline_date`；建议日独立存储。不得补造时刻；确认后的任务可回看来源快照、定位和引文。 |
| A-11 | 事项数据边界 | 只能读取与当前登录账户及个人工作区相符的数据；管理员不能读取其他用户的私人事项、事实、材料或任务；匿名请求返回 401。 |
| A-12 | 前端主流程 | 用户可从创建事项进入工作区，查看来源与候选，作出决定并看到确认后的任务；加载、空状态和错误状态均有反馈。 |
| A-13 | 启动与复现 | 新环境按 README 执行步骤可启动所交付模块；PR 记录实际运行命令和结果。 |
| A-14 | 模型超时或响应无效 | 调用状态明确标为失败或待处理；不保存伪造的候选成功结果，不生成正式任务。 |
